# Primer uso: de la instalación a un resultado medido

> Gemelo en inglés: [`FIRST-USE-EN.md`](FIRST-USE-EN.md) · El agente ejecuta · el método
> gobierna · la evidencia decide · el humano aprueba.

Este es el camino corto. Una máquina, un repositorio chico, un criterio de aceptación, un
número que se puede rastrear hasta el test que lo produjo — y una decisión de merge que sigue
siendo suya. La tesis, los ADR y la investigación vienen después, no antes.

**Verificado en:** Windows 10, git-bash, Python 3.13.12, Claude Code, un repositorio **Python**
chico con `pytest` y `pytest-cov`. Ese es el único runtime ejercitado de punta a punta al
escribir esta página. También verificado: un ciclo completo de `/uscha-devloop` en la app de
escritorio de Codex, sobre otro repositorio piloto greenfield (ADR-049). Para los demás agentes y sistemas operativos a los que el kit instala,
lea [`CROSS-PLATFORM.md`](CROSS-PLATFORM.md) y la matriz de compatibilidad del
[README](../README.md): allí la ubicación de los archivos está medida; que *carguen dentro de
cada agente* es una expectativa documentada.

**Sobre las transcripciones de abajo.** Todas son salida real de esa corrida, y completas: no
se omite ninguna fila, ni siquiera las que un primer lector todavía no necesita. Se hicieron tres
ediciones y ninguna más: las rutas absolutas se acortaron a `<repo>` / `<home>`, las líneas de más
de 120 columnas se cortaron con una continuación indentada bajo la línea que continúan para que
una pantalla angosta nunca tenga que desplazarse en horizontal, y el único `_comment` largo del
config generado está abreviado — cosa que la página vuelve a decir donde pasa. Nada fue
retipeado, inventado ni mejorado. Donde un paso no pudo ejercitarse acá, se dice en el lugar.

**No se promete cuánto tarda esto.** El kit mide evidencia, no esfuerzo.

## 1. Instalar, una vez por máquina

```bash
npx --yes @andresmassello/uscha@latest install --target claude
npx --yes @andresmassello/uscha@latest doctor --target claude
```

Hace falta Python 3.8 o superior en la máquina: el motor es biblioteca estándar de Python, sin
instalaciones de pip y sin dependencias de runtime. El paquete npm es un router delgado sobre
el instalador canónico, `uscha-kit/install-uscha.py`. Reemplace `claude` por `codex`, `cursor`,
`copilot`, `gemini`, `cline`, `pi` o `all` para los otros targets.

La instalación deja las nueve skills y el motor de medición bajo `~/.claude/skills/`.
Desde 2.7.0 termina con un informe de extras: si están las herramientas de QA del dev loop
(`code-review`, `judgment-day`, `improve`) y el engram opcional, con los comandos para agregar
lo que falte. Solo informa; no instala ninguno.

## 2. Preparar el proyecto, una vez por repositorio

```bash
cd backend-api
npx --yes @andresmassello/uscha@latest init
```

```text
Uscha 2.1.0: initialized (9 operations)
  - copy-file: <repo>/uscha.config.json
  - copy-file: <repo>/CLAUDE.md
  - copy-file: <repo>/AGENTS.md
  - copy-file: <repo>/CONSTITUTION.md
  - copy-file: <repo>/.gitattributes
  - copy-file: <repo>/.claude/scripts/uscha_statusline.py
  - copy-file: <repo>/.claude/scripts/uscha_progress.py
  - wire-statusline: <repo>/.claude/settings.json
  - wire-stop-hook: <repo>/.claude/settings.json
```

`init` **genera** `uscha.config.json` en lugar de copiar una referencia. Este es el archivo
completo que escribió para ese repositorio — el `_comment` está abreviado, todo lo demás es
byte por byte lo que quedó en disco:

```json
{

  "version": "2.1.0",
  "project": "backend-api",
  "defaults": {
    "acceptance_file": "ACCEPTANCE.md",
    "id_granularity": "file",
    "max_iterations": 5,
    "test_command_python": "pytest --cov --cov-report=xml:reports/coverage.xml --junitxml=reports/junit.xml",
    "fast_path": {
      "enabled": true,
      "max_files_changed": 3,
      "max_loc_delta": 80,
      "protected_paths": [
        "**/migrations/**",
        "**/*.approved",
        "db/**"
      ],
      "require_asserting_test": true,
      "forbid_when_golden_touched": false
    }
  },
  "repos": [
    {
      "name": "backend-api",
      "path": ".",
      "type": "python"
    }
  ],
  "integration": {
    "enabled": true
  }
}
```

Dos cosas que conviene saber antes de seguir:

- La entrada del repositorio **toma el nombre del directorio**, y su `type` sale del archivo
  marcador que hay en la raíz (`pyproject.toml` → `python`). Todo comando posterior que reciba
  `--repo` usa ese nombre.
- El archivo es mínimo a propósito: lo que *no* está escrito acá resuelve al default del motor,
  así el perfil de riesgo que declare más adelante todavía tiene algo que decidir. `version`
  registra el kit que generó el archivo.

## 3. Crear el ledger y revisar la instalación

```bash
QL="$HOME/.claude/skills/uscha-devloop/qa_ledger.py"
python "$QL" init --config uscha.config.json --out QA-LEDGER.json
python "$QL" doctor
```

`QA-LEDGER.json` es el registro del proyecto: cada paso, snapshot y veredicto queda ahí, con
checksum. `doctor` es el flutter-doctor del kit — informa, no bloquea, y sale con 0 mientras
haya advertencias pendientes:


Lea las advertencias, porque la primera es el método en miniatura:
`acceptance_file declared but missing` es lo próximo a arreglar — la sección 4 lo arregla. La
segunda, `skills de QA no encontradas como archivo`, es el aviso diciéndolo por sí mismo: esas tres
acá son built-ins del harness, no archivos, y la línea de fix dice que en ese caso se ignora. Una
advertencia nunca es una falla: `doctor` informa y sale con 0.

La fila verde de más arriba es la misma idea por el otro lado: `skills claude: current` es una
COMPARACIÓN, no una tranquilidad — el instalador copia la versión del kit junto a las skills
instaladas como `.uscha-kit-VERSION`, para que `doctor` pueda fecharlas. (El nombre lleva prefijo
porque `~/.claude/skills/` no es el directorio del kit: un archivo llamado `VERSION` ahí es de
quien lo haya escrito primero.) Antes de 2.2.0 no había copia que leer y esa línea decía
`freshness is UNMEASURED`: una ausencia nombrada. Las filas `effective ...` de abajo son la misma
disciplina aplicada al config: cada knob que un perfil gobierna, con el origen del valor vigente
— `override`, `profile <X>` o `default`.

## 4. La primera invocación de skill

En el agente, sobre un repositorio existente, el punto de entrada es el interrogador:

```bash
/uscha-adr-refine
```

Se niega a emitir artefactos hasta cerrar los huecos, y recién ahí escribe
`docs/adr/ADR-NNN.md` y `ACCEPTANCE.md` a partir de la conversación.

**No ejercitado acá.** No se corrió ningún agente al verificar esta página, así que el resto
del recorrido escribe a mano lo que habrían escrito `/uscha-adr-refine` y `/uscha-devloop`.
Todos los comandos de abajo *sí* fueron ejecutados; cada paso marcado como "no ejercitado acá"
no lo fue.

## 5. Un cambio acotado, un criterio

`ACCEPTANCE.md` en la raíz del repositorio, una línea:

```markdown
# ACCEPTANCE - backend-api

- [ ] AC-01 - `apply_discount` rechaza un porcentaje fuera de 0..100 con `ValueError`.
```

La etiqueta `AC-01` es todo el mecanismo. No es decoración: es la clave de unión entre la
oración y el caso de test que la va a cerrar.

```bash
python "$QL" readiness
```

```text
READINESS: 0.0/100 — NOT READY
  acceptance medido: 0.0% (0/1 criteria closed by a green test — measured, does not gate)
  ! static gate NEVER ran in: backend-api — dimension scored UNMEASURED (0.0), silence is not
    success
  ! NO coverage report found in: backend-api — coverage scored UNMEASURED (0.0); that is NOT the
    same fact as a measured 0%. Instrument it, or DECLARE the exemption with
    defaults.readiness_weights.coverage = 0 (config = requirement)
```

Cero, y dice por qué. Todavía no se midió nada, y el motor se niega a puntuar una dimensión sin
medir como si hubiera aprobado.

## 6. Implementarlo, y que el test lleve el identificador

```python
# src/backend_api/discount.py
def apply_discount(cents, percent):
    if not 0 <= percent <= 100:
        raise ValueError("percent must be between 0 and 100")
    return cents - cents * percent // 100
```

```python
# tests/test_discount.py
import pytest

from backend_api.discount import apply_discount


def test_applies_a_percentage():
    assert apply_discount(1000, 10) == 900


def test_AC_01_rejects_a_percentage_outside_the_range():
    with pytest.raises(ValueError):
        apply_discount(1000, 150)
```

El nombre del test lleva `AC_01`. Corra el comando de test del proyecto — el que `init` escribió
en `defaults.test_command_python` — y después deje que el motor ingiera lo que produjo:

```bash
python -m pytest --cov --cov-report=xml:reports/coverage.xml --junitxml=reports/junit.xml
python "$QL" snapshot --repo backend-api --phase post
python "$QL" readiness
```

```text
[qa_ledger] snapshot backend-api (post): coverage=100.0% (found=True), tests=2 (found=True),
    freshness=fresh, origin=d090593b/dirty, prod_loc=248, test_loc=7

READINESS: 45.0/100 — NOT READY
  acceptance medido: 100.0% (1/1 criteria closed by a green test — measured, does not gate)
  · measured but unticked: AC-1 — there is a green testcase; tick the checkbox if the criterion
    is done
  ! static gate NEVER ran in: backend-api — dimension scored UNMEASURED (0.0), silence is not
    success
```

Ese es un resultado normal, y es la frase que todo el kit existe para imprimir: **measured but
unticked** (medido pero sin tildar). El motor encontró un caso de test en verde nombrado según
`AC-01`, en un reporte que él no escribió, producido por una corrida cuya evidencia está
`fresh` respecto del estado actual del código. Cerró el criterio por su cuenta — y no le va a
tildar la casilla.

El puntaje es 45.0 y no más alto porque otras dimensiones siguen **UNMEASURED**: no corrió
ningún gate estático. UNMEASURED no es cero, y no es un aprobado; es una ausencia con nombre y
con arreglo nombrado.

## 7. La decisión humana

Tilde la casilla, porque la evidencia lo habilita:

```markdown
- [x] AC-01 - `apply_discount` rechaza un porcentaje fuera de 0..100 con `ValueError`.
```

```text
READINESS: 60.0/100 — IN PROGRESS
  acceptance medido: 100.0% (1/1 criteria closed by a green test — measured, does not gate)
  ! static gate NEVER ran in: backend-api — dimension scored UNMEASURED (0.0), silence is not
    success
```

En el loop completo el agente lo lleva hasta acá y se detiene. `/uscha-devloop` planifica desde
el ADR, construye, corre un loop de revisión con puertas por severidad que converge en lugar de
girar para siempre, y frena en la puerta del merge:

```bash
/uscha-devloop
```

**No ejercitado acá.** El merge es del humano, siempre. El trabajo del kit termina al
entregarle un número auditable; abrir y mergear el pull request es suyo.

## 8. Cuando falta la evidencia

Dos veredictos que va a encontrar temprano, y qué pide cada uno.

**`narrated-only` — tildó una casilla que los reportes no respaldan.** Si tilda un criterio sin
un test verde que le corresponda, el motor lo dice y no lo cierra:

```text
READINESS: 45.0/100 — NOT READY
  acceptance medido: 50.0% (1/2 criteria closed by a green test — measured, does not gate)
  ! narrated-only: AC-2 — checkbox ticked WITHOUT a green 'AC-n' testcase in the reports,
    without a green corpus run carrying it and without a green 'AC-n' smoke check (measured
    beats narrated: does NOT close)
  ! static gate NEVER ran in: backend-api — dimension scored UNMEASURED (0.0), silence is not
    success
```

*Próxima acción:* escriba un test cuyo nombre lleve el identificador, corra el comando de test,
vuelva a correr `snapshot`. O destilde la casilla. No discuta con el ledger.

**`UNMEASURED` — no corrió nada, así que no se sabe nada.** Una dimensión sin reporte se puntúa
como UNMEASURED, nunca como un 0% aprobado.

*Próxima acción:* instruméntela (corra la herramienta, produzca el reporte, `snapshot` de
nuevo), o **declare la excepción** en la configuración: la línea de advertencia nombra la clave
exacta. Una dimensión que decide no medir es una decisión que se escribe, no un silencio.

## 9. Tres rutas desde acá

Cada una es una skill existente, no un modo nuevo.

| Si quiere… | Ruta |
|---|---|
| **Arrancar un proyecto** desde una idea | [`/uscha-discovery`](../uscha-kit/skills/uscha-discovery/SKILL.md) → [`/uscha-devloop`](../uscha-kit/skills/uscha-devloop/SKILL.md) |
| **Cambiar un sistema existente** | [`/uscha-adr-refine`](../uscha-kit/skills/uscha-adr-refine/SKILL.md) → [`/uscha-devloop`](../uscha-kit/skills/uscha-devloop/SKILL.md) |
| **Migrar comportamiento heredado** | [`/uscha-characterize`](../uscha-kit/skills/uscha-characterize/SKILL.md) → un humano aprueba el golden → [`/uscha-devloop`](../uscha-kit/skills/uscha-devloop/SKILL.md) |

Algo de la tercera ruta que no es un detalle. **Un golden capturado registra el comportamiento
que el sistema tiene, no el que usted quiere.** `/uscha-characterize` corre el código original,
escribe `.received` y se detiene: el agente nunca escribe ni renombra un archivo `.approved`
(INV-GOLDEN-01). Aprobar un golden congela lo que hay, bugs incluidos. Un bug congelado es un
bug que fijó, nunca un requisito que decidió. Decida cuáles de los comportamientos observados
son requisitos *antes* de aprobar, y deje registrados los que no lo son.
