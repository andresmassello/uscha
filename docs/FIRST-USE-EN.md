# First use: from install to one measured result

> Spanish twin: [`FIRST-USE.md`](FIRST-USE.md) · The agent executes · the method governs ·
> evidence decides · the human approves.

This is the short path. One machine, one small repo, one acceptance criterion, one number you
can trace back to the test that produced it — and a merge decision that stays yours. The
thesis, the ADRs and the research come after, not before.

**Verified on:** Windows 10, git-bash, Python 3.13.12, Claude Code, a small **Python** repo
with `pytest` and `pytest-cov`. That is the one runtime exercised end to end while writing this
page. Also verified: a full `/uscha-devloop` cycle on the Codex desktop app, on a separate
greenfield pilot repo (ADR-049). For the other agents and operating systems the kit installs to, read
[`CROSS-PLATFORM.md`](CROSS-PLATFORM.md) and the compatibility matrix in the
[README](../README.md) — placement there is measured; *loading inside every agent* is a
documented expectation.

**About the transcripts below.** Every one of them is real output from that run, whole: no
row is dropped, not even the ones a first reader will not need yet. Three edits were made and no
others: absolute paths were shortened to `<repo>` / `<home>`, lines longer than 120 columns were
wrapped with a continuation indented under the line it continues so a narrow screen never has to
scroll sideways, and the one long `_comment` in the generated config is abridged — which the page
says again where it happens. Nothing was retyped, invented, or improved. Where a step could not be
exercised here, it says so in place.

**No promise is made about how long this takes.** The kit measures evidence, not effort.

## 1. Install, once per machine

```bash
npx --yes @andresmassello/uscha@latest install --target claude
npx --yes @andresmassello/uscha@latest doctor --target claude
```

Python 3.8 or newer must be on the machine — the engine is Python standard library, with no
pip installs and no runtime dependencies. The npm package is a thin router over the canonical
installer, `uscha-kit/install-uscha.py`. Replace `claude` with `codex`, `cursor`, `copilot`,
`gemini`, `cline`, `pi`, or `all` for the other targets.

The install puts the nine skills and the measurement engine under `~/.claude/skills/`.

## 2. Prepare the project, once per repo

```bash
cd backend-api
npx --yes @andresmassello/uscha@latest init
```

```text

  - copy-file: <repo>/CLAUDE.md
  - copy-file: <repo>/AGENTS.md
  - copy-file: <repo>/CONSTITUTION.md
  - copy-file: <repo>/.gitattributes
  - copy-file: <repo>/.claude/scripts/uscha_statusline.py

file it wrote for that repo — the `_comment` is abridged, everything else is byte for byte
what landed on disk:

        "**/migrations/**",
        "**/*.approved",

      ],
      "require_asserting_test": true,
      "forbid_when_golden_touched": false
    }
  },

    }
  ],
  "integration": {
    "enabled": true
  }

```

Two things worth knowing before you read further:

- The repo entry is **named after the directory**, and its `type` comes from the marker file at
  the root (`pyproject.toml` → `python`). Every later command that takes `--repo` uses that
  name.
- The file is minimal on purpose: what is *not* written here resolves to the engine default, so
  a risk profile you declare later still has something left to decide. `version` records the
  kit that generated the file.

## 3. Create the ledger, then check the installation

```bash
QL="$HOME/.claude/skills/uscha-devloop/qa_ledger.py"
python "$QL" init --config uscha.config.json --out QA-LEDGER.json
python "$QL" doctor
```

`QA-LEDGER.json` is the project's record: every step, snapshot and verdict lands there, and it
is checksummed. `doctor` is the flutter-doctor of the kit — it reports, it does not gate, and
it exits 0 while warnings remain:

Read the warnings, because the first one is the method in miniature:
`acceptance_file declared but missing` is the next thing to fix — section 4 fixes it. The second,
`skills de QA no encontradas como archivo`, is the notice telling you so itself: those three are
harness built-ins here, not files, and the fix line says to ignore it in that case. A warning is
never a failure — `doctor` reports and exits 0.

The green row further up is the same idea from the other side: `skills claude: current` is a
COMPARISON, not a reassurance — the installer copies the kit's version beside the installed skills
as `.uscha-kit-VERSION`, so `doctor` can date them. (The name is namespaced because
`~/.claude/skills/` is not the kit's directory: a file called `VERSION` there would belong to
whoever wrote it first.) Before 2.2.0 there was no copy to read and that line said
`freshness is UNMEASURED`: not a pass, a named absence. The `effective ...` rows below are the
same discipline applied to the config: every profile-owned knob, with the origin of the value in
force — `override`, `profile <X>` or `default`.

## 4. The first skill invocation

In the agent, on an existing repo, the entry point is the interrogator:

```bash
/uscha-adr-refine
```

It refuses to emit artifacts until the gaps are closed, and then writes `docs/adr/ADR-NNN.md`
plus `ACCEPTANCE.md` out of the conversation.

**Not exercised here.** No agent was run while verifying this page, so the rest of the
walkthrough writes by hand what `/uscha-adr-refine` and `/uscha-devloop` would have written.
Every command below *was* executed; every step marked "not exercised here" was not.

## 5. One bounded change, one criterion

`ACCEPTANCE.md` at the repo root, one line:

```markdown
# ACCEPTANCE - backend-api

- [ ] AC-01 - `apply_discount` refuses a percentage outside 0..100 with `ValueError`.
```

The `AC-01` tag is the whole mechanism. It is not decoration — it is the join key between the
sentence and the test case that will close it.

```bash
python "$QL" readiness
```

```text
READINESS: 0.0/100 — NOT READY
  acceptance medido: 0.0% (0/1 criteria closed by a green test — measured, does not gate)
  ! static gate NEVER ran in: backend-api — dimension scored UNMEASURED (0.0), silence is not
    success
  ! NO coverage report found in: backend-api — coverage scored UNMEASURED (0.0); that is NOT the
    same fact as a measured 0%. Instrument it, or DECLARE the exemption with
    defaults.readiness_weights.coverage = 0 (config = requirement)
```

Zero, and it says why. Nothing has been measured yet, and the engine refuses to score an
unmeasured dimension as if it had passed.

## 6. Implement it, and let the test carry the id

```python
# src/backend_api/discount.py
def apply_discount(cents, percent):
    if not 0 <= percent <= 100:
        raise ValueError("percent must be between 0 and 100")
    return cents - cents * percent // 100
```

```python
# tests/test_discount.py
import pytest

from backend_api.discount import apply_discount


def test_applies_a_percentage():
    assert apply_discount(1000, 10) == 900


def test_AC_01_rejects_a_percentage_outside_the_range():
    with pytest.raises(ValueError):
        apply_discount(1000, 150)
```

The test's name carries `AC_01`. Run the project's test command — the one `init` wrote into
`defaults.test_command_python` — then let the engine ingest what it produced:

```bash
python -m pytest --cov --cov-report=xml:reports/coverage.xml --junitxml=reports/junit.xml
python "$QL" snapshot --repo backend-api --phase post
python "$QL" readiness
```

```text
[qa_ledger] snapshot backend-api (post): coverage=100.0% (found=True), tests=2 (found=True),
    freshness=fresh, origin=d090593b/dirty, prod_loc=248, test_loc=7

READINESS: 45.0/100 — NOT READY
  acceptance medido: 100.0% (1/1 criteria closed by a green test — measured, does not gate)
  · measured but unticked: AC-1 — there is a green testcase; tick the checkbox if the criterion
    is done
  ! static gate NEVER ran in: backend-api — dimension scored UNMEASURED (0.0), silence is not
    success
```

That is a normal result, and it is the sentence the whole kit exists to print: **measured but
unticked**. The engine found a green test case named after `AC-01`, in a report it did not
write, produced by a run whose evidence is `fresh` against the current code state. It closed
the criterion on its own — and it will not tick your checkbox for you.

The score is 45.0 and not higher because other dimensions are still **UNMEASURED**: no static
gate has run. UNMEASURED is not zero, and it is not a pass; it is a named absence with a
named fix.

## 7. The human decision

Tick the box, because the evidence says you may:

```markdown
- [x] AC-01 - `apply_discount` refuses a percentage outside 0..100 with `ValueError`.
```

```text
READINESS: 60.0/100 — IN PROGRESS
  acceptance medido: 100.0% (1/1 criteria closed by a green test — measured, does not gate)
  ! static gate NEVER ran in: backend-api — dimension scored UNMEASURED (0.0), silence is not
    success
```

In the full loop the agent gets you to this point and stops. `/uscha-devloop` plans from the
ADR, builds, runs a severity-gated review loop that converges instead of looping forever, and
halts at the merge gate:

```bash
/uscha-devloop
```

**Not exercised here.** The merge is the human's, always. The kit's job ends at handing you a
number you can audit; opening and merging the pull request is yours.

## 8. When the evidence is missing

Two verdicts you will meet early, and what each one wants from you.

**`narrated-only` — you ticked a box the reports do not back.** Tick a criterion with no
matching green test and the engine says so, and does not close it:

```text
READINESS: 45.0/100 — NOT READY
  acceptance medido: 50.0% (1/2 criteria closed by a green test — measured, does not gate)
  ! narrated-only: AC-2 — checkbox ticked WITHOUT a green 'AC-n' testcase in the reports,
    without a green corpus run carrying it and without a green 'AC-n' smoke check (measured
    beats narrated: does NOT close)
  ! static gate NEVER ran in: backend-api — dimension scored UNMEASURED (0.0), silence is not
    success
```

*Next action:* write a test whose name carries the id, run the test command, re-run `snapshot`.
Or untick the box. Do not argue with the ledger.

**`UNMEASURED` — nothing ran, so nothing is known.** A dimension with no report is scored
UNMEASURED, never as a passed 0%.

*Next action:* instrument it (run the tool, produce the report, `snapshot` again), or **declare
the exemption** in the config — the advisory line names the exact key. A dimension you decide
not to measure is a decision you write down, not a silence.

## 9. Three routes from here

Each of these is an existing skill, not a new mode.

| You want to… | Route |
|---|---|
| **Start a project** from an idea | [`/uscha-discovery`](../uscha-kit/skills/uscha-discovery/SKILL.md) → [`/uscha-devloop`](../uscha-kit/skills/uscha-devloop/SKILL.md) |
| **Change an existing system** | [`/uscha-adr-refine`](../uscha-kit/skills/uscha-adr-refine/SKILL.md) → [`/uscha-devloop`](../uscha-kit/skills/uscha-devloop/SKILL.md) |
| **Migrate legacy behavior** | [`/uscha-characterize`](../uscha-kit/skills/uscha-characterize/SKILL.md) → a human approves the golden → [`/uscha-devloop`](../uscha-kit/skills/uscha-devloop/SKILL.md) |

One thing about the third route that is not a detail. **A captured golden records the behavior
the system has, not the behavior you want.** `/uscha-characterize` runs the original code,
writes `.received`, and stops — the agent never writes or renames an `.approved` file
(INV-GOLDEN-01). Approving a golden freezes what is there, bugs included. A frozen bug is a
bug you have pinned, never a requirement you have decided. Decide which observed behaviors are
requirements *before* you approve, and record the ones that are not.
