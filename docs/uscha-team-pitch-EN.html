01 the current situation

Five devs, five different methods.

Everyone configured Claude Code as they saw fit. And each person's judgment is sound -- but it is their own.

The context

It lives in each session's chat: what was decided, why, and what was left out. The chat gets compacted, deleted, lost.

The setup

A different CLAUDE.md (or none), memory prompts, different skills. The same request gives different results depending on who handles it.

The evidence

?The agent said it is ready and the tests pass.-- Which tests-- Do they assert what matters-- No one measures it -- people trust the narrative.

None of these things hurt today. They hurt three weeks from now, when someone else inherits the work.

02 a fictional story -- but one you have seen happen

Friday: Vale ships coupons.

Vale builds the coupon feature with Claude Code, as always: straight into the code, iterating in the chat. It turns out well. Midway through, Sales asks her for one detail on Slack: a coupon that expired less than 24 hours ago is still accepted (a grace period). She explains it to the agent in the chat, the agent implements it, tests are green, merge.

  claude -- Vale's session -- Friday 17:40
> Sales asks: if the coupon expired less than 24 hours ago, accept it anyway (grace period)
Understood -- I'll add a 24-hour grace window to expiration validation?
[ok] 14 tests passed -- --done, implemented and tested?
-- merge. The reason for the --weird bug-- stayed here, in this chat. And no one will read this chat.

Where was the grace-period rule documented? In a Slack thread that will scroll into oblivion and in a Claude Code chat that gets compacted. The code contains an uncommented expiredAt + 24h. There is no SPEC, no test that explicitly asserts it.

Martin's agent is not lying: it guesses with confidence -- without Vale's context, the grace period IS indistinguishable from a bug. The tests pass because they never pinned down that rule. The following Monday, Sales reports that --coupons are broken-- at the worst possible time.

04 the honest postmortem

No one did anything wrong.
And everything went wrong.

failure 1

The --why-- lived in the chat

The decision (a 24-hour grace period) never made it into a versioned file. A code comment-- It explains, but it does not protect: nothing tests it, it does not stop a merge, and the agent that --normalizes-- it deletes it with the line.

failure 2

Different setups, different results

Martin's agent does not behave like Vale's: another CLAUDE.md, different skills, another memory. The behavior was not reproducible.

failure 3

?Done-- was a narrative

?Green tests-- sounded like evidence, but no one measured whether the tests asserted what mattered. The critical rule did not have a single test.

failure 4

Nothing stopped the second agent

What about code review-- The reviewer had the same context as Martin: zero. The diff looked like a legitimate off-by-one fix with green tests -- and they approved it for the same reason the agent proposed it. The missing piece was context, not diligence.

The problem is neither the tool nor the developer. Knowledge lived in places that die -- and no shared method required it to live in the repo.
05 the method

Uscha: you bring the idea,
the method builds the rest.

A spec-driven methodology that starts before the spec, moves forward only with captured evidence, and stops at a human-approved merge. We all run it the same way, against the same files, with the same Claude Code skills.

station evidence gate human-owned internal loop
06 the same story, with a method -- act 1

Replay: Vale starts with /uscha-discovery.

Before touching code, 30 minutes of questioning. The skill does not agree with everything -- it asks until the shape is clear: contradictions, fuzzy terms, failure modes. One question at a time.

  claude -- /uscha-discovery -- Friday 10:00
discovery> What exactly happens to a coupon that expired an hour ago-- A hard
rejection, or is there business tolerance?
> good question-- Sales wants a 24-hour grace period. I'll confirm it and let you know
discovery> Then confirmed: I'll write it in the SPEC as an explicit rule with its
rationale, and as a testable acceptance criterion in ACCEPTANCE.md.

The question that no one asked in the real story is asked here by the method -- and the answer does not die in a chat: it crystallizes in SPEC.md + ACCEPTANCE.md + an ADR when there is a trade-off decision. Committed. In the repo.

A compliant interviewer inherits your blind spots and hands them back formatted as a plan. Friction is the deliverable.discovery operating rule
07 the same story, with a method -- act 2

Vale builds with /uscha-devloop:
evidence, not narrative.

The orchestrator takes SPEC + ACCEPTANCE, builds, and runs a QA loop that measures instead of believing. What BLOCKS comes from real artifacts parsed by qa_ledger.py -- tests, coverage, linters, fact gates. What the agent reports about itself is recorded separately, as narrative -- and a measured red always vetoes a narrated green.

measured

Ledger

Coverage, tests, and linter findings parsed from real XML. Self-reports are recorded separately: narrative, not data.

measured

Fact gates

gate-check (does the change weaken tests/thresholds?) and other gates are persisted with log-gate: one red blocks convergence.

human

Merge gate

The loop opens the PR, shows readiness (KPI 0-100) with its breakdown, and stops. A person merges. Always.

The grace rule now has its criterion in ACCEPTANCE.md and a test that explicitly asserts it. It is no longer a mysterious + 24h: it is specified and pinned behavior.

08 the same story, with a method -- act 3

The handoff: Martin inherits
files, not mysteries.

Three weeks later, Martin picks up coupons. His agent -- the same shared setup, the same skills -- reads the same files the method wrote: SPEC, ADRs, ACCEPTANCE.

  claude -- Martin's session -- replay
> why does expiration validation add 24 hours-- it looks like a bug
It is not a bug: SPEC.md expiration documents the 24-hour grace period requested by
Sales (2026-06-12), and an acceptance criterion pins it down.
If you want to change it, it is an amendment to the SPEC -- not a silent fix.
[ok] the rule survives -- and if an agent deleted its test, gate-check marks it BLOCKER

Double defense: the intent is written where the agent reads it (versioned files), and even if an agent tried to --fix-- the rule, the test that asserts it turns red and gate-check catches attempts to delete or disable it -- a BLOCKER convergence will not let through (weakening assertions is flagged for review; --strict gates it).

Truth lives in versioned files. The chat is where we think; the repo is where we remember.
09 honest adoption

What changes in your day
(and what does NOT).

changes -- 4 habits
  • Before coding anything non-trivial: /uscha-discovery (new idea) or /uscha-adr-refine (known feature). Let it question you.
  • Decisions go into the repo immediately: SPEC, ADR, ACCEPTANCE. Not at the end, not in chat.
  • The loop runs and persists QA: /uscha-devloop measures with the ledger; fact gates are recorded with log-gate.
  • The PR stops at merge. A human merges after reading the diff -- never the agent.
does NOT change
  • Trivial changes (one-liner, config): build + test and done. The method does NOT trail behind a one-line fix.
  • Spikes and prototypes: no SPEC. Write down what you learn; specify only what survives.
  • P0 hotfix: fix it first. The retrospective SPEC/ADR is due within 24 hours -- a designed escape valve, not an improvised one.
  • Your way of thinking. The method does not code for you: it makes you state what you want BEFORE, and prove what happened AFTER.
10 the rule that orders everything

Facts block.
Conjectures only advise.

A gate that reads a FACT (bytes, XML, diff structure) can stop work. A gate that guesses about prose can only whisper -- because a gate with false positives gets turned off, and a dead gate is worse than none.

GateReads
gate-checkdiff structure: deleted/disabled tests, lowered or removed thresholdsBLOCKS
golden-diffbytes vs .approved (migrations -- the only artifact the agent does not write: a PreToolUse hook blocks it)BLOCKS
simplicity-checkdiff budget: size, nesting, hunks (OVERBUILT = trim it)BLOCKS
structural spec-checkis there an out-of-scope section-- are there acceptance criteria-- (it either exists or it does not)BLOCKS
prose spec-checkheuristic: vague criteria, no metricADVISES
readinessstate KPI 0-100 (with hard caps: red tests <=35, open BLOCKER <=65)REPORTS

And this closes Vale and Martin's story: what is measured beats what is narrated -- a red test snapshot vetoes any agent's --green tests-- report.

11 what you are thinking

The three objections
(and the honest answers).

"more ceremony"

Rigor scales with blast radius. A UI fix runs build+test and nothing else. The full machine is for work that can break expensive things -- and there, ceremony is cheaper than the coupon incident.

"it will slow me down"

It slows you down for 30 minutes at the start -- where friction is cheap -- to save you from the expensive failure: confidently building the wrong thing. What Martin lost debugging on Monday was MORE than all of Vale's discovery.

"my way works"

It works solo. It breaks at handoff -- and no one works alone here. The method does not replace your judgment: it makes it legible to whoever comes next. Your self three months from now is also --whoever comes next."

Behavior can be replicated; memory must be earned. Shared setup solves the first; files in the repo solve the second.
