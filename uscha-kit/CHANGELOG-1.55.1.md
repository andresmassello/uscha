# uscha-kit 1.55.1 — AC-03 is measured, not declared (2026-07-26)

An external audit of the now-public repo found private project names in four **tracked** files
while `ACCEPTANCE.md` carried AC-03 ("zero references to client or private project names")
**ticked by hand**. A hand-ticked green over a criterion that was factually false, with the gate
itself reading UNMEASURED. In the repository of a method whose first rule is *measured beats
narrated*. Smoke suite: 394/394 on Windows, Linux and macOS.

## Two holes, not one
**The list was invisible.** It lived only in an untracked `.uscha-private-names`, so CI emitted
`<skipped/>` on every public run — and nobody, not even the author, could see that the list was
incomplete. None of the four leaked terms were in it.

**The scan was near-sighted.** It walked `uscha-kit/` and `README.md` only. The names were in
`audits/` and `formats/`. **Even a complete list would not have found them.**

## What changed
- **`.uscha-private-names.sha256` is COMMITTED**: one SHA-256 per lowercased token, generated by
  `uscha-kit/tests/private-names-hash.py`. CI now measures AC-03 instead of skipping it, without
  publishing the names the criterion exists to keep out.
- **The scan covers every TRACKED file** in the repo — tracked, deliberately: the criterion is
  about what the kit and its docs *contain*, i.e. what is published. Scanning the filesystem
  flagged an untracked local transcript, and training the operator to ignore a red AC-03 would
  be worse than not having it. Untracked artifacts are `.gitignore`'s job.
- The untracked plaintext list stays as the release machine's **stricter superset**: it can hold
  prefixes and regexes, which a hash cannot express.

Proven by mutation: planting a listed name in a tracked file turns AC-03 **red**, and removing
it turns it green again. AC-03 is re-ticked — wired first, then re-claimed (repo rule 2).

## Honest limits, stated in the generator itself
A hash matches **whole tokens only** — no prefixes, no regexes; those terms stay local-only and
are reported as unhashable rather than silently dropped. And an unsalted SHA-256 is **not secret
against a targeted guess**: someone who already suspects a name can hash it and compare. It
stops casual reading, grepping and search indexing; it is not a vault. A secret salt was
rejected on purpose — it would put the gate back behind invisible config, which is the exact
failure this replaces.
