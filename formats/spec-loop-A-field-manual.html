Complete documentation · instantiation in Claude Code

You bring the idea. The method builds the rest.

spec-loop is a spec-driven, tool-agnostic methodology that begins before the spec: from a vague idea and reference material, the assistant proposes the shape of the system, the human decides, and only then is the work specified, built, and advanced on evidence alone. This manual documents the instantiation in Claude Code via the dev-loop-kit.

Flow: Idea → Discovery → Ready → SPEC → ADR? → Build → Verify → Evidence → Human gate
in the kitnewproposal — status is stated per clause. No smoke: whatever isn't implemented is flagged.
§1 · Definition

A methodology that starts before the specification.

The premise: most spec-driven work assumes you already know what to build. spec-loop rejects that. The expensive failure isn't a bad implementation — it's a confident implementation of the wrong shape.

So the first move is Discovery: turn a vague idea plus reference material into a proposed system shape, which the human accepts, alters, or rejects. Only after the shape is agreed does specification begin. From there, every downstream step advances on captured evidence rather than the agent's narration, and the whole apparatus stops short of merge — the human holds that gate.

ContractThe nine-stage flow is the spine of the rest of this manual. Each clause below either produces or consumes one of its artifacts.
§2 · Discovery & refine in the kit

Two entry skills, one governing principle.

The front of the loop is two skills that produce clarity, never code. Both are constrained to Read, Write, Glob, Grep; /discovery adds WebFetch to read manuals, PDFs, and URLs.

/discovery — "I have an idea, not a shape"

A one-on-one adversarial interview that proposes candidate entities and endpoints, surfaces contradictions, and forces three or four real decisions from the human. It emits no artifact until it converges on a shape.

/adr-refine — "I know the what, precision is missing"

A feature inside a system whose shape is already known. The interview paints the edges: dirty inputs, error paths, idempotency, inviolable constraints, and what is explicitly out of scope.

The principle that defines them

Grill, don't agree. A discovery where the assistant agreed with everything has failed. The value lives in the questions — the contradictions, the fuzzy terms, the missing failure modes — not in validation.

Why adversarialAn agreeable interviewer inherits the human's blind spots verbatim. The friction is the product.
§3 · The document package

The conversation crystallizes into files in the repo.

Discovery writes the package directly into the repo as decisions settle — it doesn't hoard everything for the end. Downstream, the build reads from these files, not from the chat.

FileWhat it holds
CONTEXT.mdDomain glossary. Sharpens fuzzy language — is "account" a Customer or a User?
DOMAIN-MODEL.mdThe proposed core entities and relations — the shape the human approved.
SPEC.mdObjective, risk, scope, behavior, inputs/outputs/errors, acceptance, test plan, operation, rollback.
docs/adr/*.mdOne per durable decision. Carries an Implementation Plan and a checkbox Verification block — an executable spec.
ACCEPTANCE.mdDefinition of Done as - [ ] plus success metrics. The file the readiness KPI measures.
RISKS.mdResidual risks, assumptions, points needing human approval.
HANDOFF.mdWhat to read before coding, hard "do not" rules, required evidence.

Why files even when it's all one Claude Code session: context resets (a new session, a /clear, a compaction) lose the chat; sub-agents read files; CI or a teammate builds from the repo; the audit trail stays durable. The truth lives in versioned files.

InvariantIf a fact isn't in a versioned file, the loop does not know it. Chat is scratch; the repo is memory.
§4 · SPEC ≠ ADR

Two documents, two different questions.

If it describes observable behavior, it belongs in the SPEC. If it justifies a choice between alternatives, it belongs in an ADR. Nearly every non-trivial change needs a SPEC; only some warrant a formal ADR.

An ADR is written with judgment

Write one only when the decision satisfies all three tests: hard to reverse, surprising without context, and the result of a real trade-off. Otherwise it is noise that buries the decisions that matter.

# docs/adr/ADR-NNN-<slug>.md
## Status: Accepted        # proposed/accepted/deprecated/superseded
## Context / Forces
## Alternatives: A) … B) … C) …
## Decision · Reasons · Consequences (+/-)
## Implementation Plan      # affected paths · patterns · tests
## Verification
- [ ] <criterion an agent can check>

The Implementation Plan is what makes an ADR executable: the agent reads it and implements without re-asking. The code links back with // ADR: <slug>, which makes a later supersede safe — you can find everything the decision governs.

TestHard to reverse · surprising without context · a real trade-off. Miss one → it's a SPEC line, not an ADR.
§5 · The Constitution layer in the kit

Above the ADRs sits what no decision may violate.

An ADR chooses between alternatives. The CONSTITUTION forbids: it records the invariants that no ADR or SPEC may override, whatever trade-off wins. It is the project's hierarchy of truth.

SPEC says what must happen. ADR says why this shape was chosen. CONSTITUTION says what is never acceptable. An ADR may choose MSSQL vs Redis to cache a record; an ADR may not choose "store the certificate in plaintext" — the constitution vetoes that before alternatives are even discussed.

## CONSTITUTION.md — project invariants
# Security (non-negotiable)
- Secrets never in logs or the repo       # CWE-532 / CWE-798
- All external input validated             # CWE-20
- Parameterized SQL only                   # CWE-89
# Domain (fiscal)
- Mandatory idempotency when issuing CAE
- Sequential numbering, no logical gaps
# Operation
- No destructive migration without rollback
- No merge without a human gate

Since 1.1.0 it is a first-class layer: templates/CONSTITUTION.md, versioned, invariants mapped to CWE. Discovery and adr-refine extend it; an ADR that contradicts it escalates rather than being approved. /dev-loop reads it in Phase 0. A violation is logged as a BLOCKER — it caps readiness at ≤65 and blocks convergence by construction.

Golden invariantNewest constitutional rule: no module enters migration without a captured golden baseline; the agent never authors .approved files. Maps to CWE-440.
§6 · Risk-based workflow

Not every change carries the same weight.

Opening question for any change: what can this break, and what does it cost if it does? Risk scales the apparatus — a profile-A change never drags the full machinery behind it.

§7 · /dev-loop, phase by phase in the kit

A converging orchestrator, not an infinite chase.

The dev-loop is a multi-repo, spec-driven orchestrator. It takes the ADR set plus ACCEPTANCE.md, builds, and runs a severity-gated review loop that converges instead of looping forever, with the tests as a guardrail between steps. It halts at the merge gate. Three non-negotiable principles govern it: converge, don't chase zero; tests are a guardrail, not the finale; generating tests is not running tests.

  1. Setup. qa_ledger.py init. The config lists each repo and its type (maven/flutter); other repos mount via --add-dir.
  2. Phase 0 — Plan (ADR-first). ADRs + acceptance are the input. Missing acceptance? Stop and run /adr-refine. Acceptance criteria become Phase-1 contract tests.
  3. Phase 1 — Coverage gate → conditional characterization. Snapshot pre + check-coverage. Above threshold, the existing suite is the guardrail; below it, write characterization/contract tests at the edge — and let the human review them before trusting them.
  4. Phase 2 — Build. Implement per plan, one commit per logical step. Consult the constitution before touching governed areas; stop and propose an ADR on a new dependency, a new pattern, or a contradiction.
  5. Phase 3 — QA loop. Run the tools in order (code-review → judgment-day → improve-deep). One pass of all = one cycle. Apply only fixes at or above the severity gate; the rest to ISSUES-DEFERRED.md. Run tests, log the step, ingest the static gate. End-of-cycle advisories: converged, oscillation.
  6. Phase 4 — Integration / contract. With all repos mounted, run cross-repo contract tests. Per-repo green does not mean the seams are green.
  7. Phase 5 — Verify. With stable code, write the fine-grained coverage you deferred. Full suite green + coverage ≥ threshold.
  8. Phase 6 — PR. Open it, confirm CI green, and stop. The human merges.
  9. Phase 7–8 — Smoke + docs. Manual smoke checklist, then summary + readiness + /sys-doc; retrospective pulled from the ledger.
Failure modeThe "Ralph Wiggum loop": the agent emits the done token too early. An objective gate — not an opinion — is the only fix.
§8 · Captured evidence

Evidence is produced by execution, never narrated.

The crack the method closes: if the same agent that makes a change also writes the ledger, it can record exit_code: 0 without running anything. The guarantee holds only when evidence is produced by execution — qa_ledger.py parses real artifacts, it does not transcribe the agent's claims.

# the ledger does NOT trust the agent — it parses files
coverage  ← target/site/jacoco/jacoco.xml
tests     ← target/surefire-reports/TEST-*.xml
static    ← checkstyle-result.xml · pmd.xml · spotbugsXml.xml
LOC       ← its own count (prod vs test), pure stdlib

Hard rule

Absent = no evidence, never "OK". A report that exists but is empty credits the fix; an absent report means the gate didn't run. A tool that didn't run is never invented as green.

Maker ≠ checkerThe one who makes doesn't graduate the work; a checker in fresh context validates it — Anthropic's evaluator-optimizer, Dec 2024.
§9 · qa_ledger.py in the kit

The measurement engine — deterministic by design.

Pure stdlib, Python 3.8+, no dependencies. It owns everything that must be exact and reproducible. The judgments — did it converge, is it oscillating, do we escalate — are made by the skill reading the data; the script only exposes deterministic helpers.

SubcommandWhat it does
initBuilds the ledger from dev-loop.config.json.
snapshotMeasures coverage / tests / LOC (--phase pre|post).
check-coverageExit 0 if ≥ threshold — the Phase-1 gate.
log-stepRecords a QA-tool pass: reported / fixed / deferred / suppressed / tests-passed / fingerprint.
ingest-gateParses the linters, normalizes severity, computes real fixed by diffing finding-IDs.
convergedAdvisory: last cycle clean + static gate clean across all linters.
oscillationAdvisory: detects a period-2 fingerprint repeat (pass N == pass N-2).
readinessThe project-state KPI: 0–100 with weights and hard caps.
rebuildSpec-completeness test. Baseline signs the system; compare scores regeneration (COVERS / PARTIAL / DIVERGE).
golden-diffByte-compares .received vs .approved. Field truth, human-approved — the agent doesn't author it.
Division of laborScript = exact and reproducible. Skill = judgment over the numbers. Never the reverse.
§10 · Gates & measurement

Facts block; guesses advise.

The guiding principle of the gate architecture: a gate that reads facts may block convergence; a gate that guesses over prose may only advise. A natural-language heuristic that blocks throws false positives, the developer turns it off, and you're left with a dead gate — the exact erosion the method fights.

GateReads
golden-diffbyte-comparison vs .approvedBLOCKS
pit-checkPIT XML (mutation testing)BLOCKS
gate-checkdiff structure (deleted tests/thresholds)BLOCKS
readiness / rebuildreports; COVERS/DIVERGEBLOCKS
static gateCheckstyle/PMD/SpotBugs/FindSecBugsBLOCKS
spec-check · abstractionsheuristic over proseADVISES

The static gate is normalized to one severity scale by ingest-gate (Checkstyle error→HIGH, PMD priority 1→BLOCKER, and so on) and FindSecBugs is separated from SpotBugs. Fact gates run in CI, not in the developer's face.

Uncorrelated checkerOsmani's finding: one tool caught 93.4% of what four did — value is in an uncorrelated second opinion, not in stacking similar linters.
§11 · The outer loop proposal

Autonomy earns its cost, or costs more than it returns.

spec-loop is the rigorous inner loop. The outer loop is the heartbeat that would trigger it on a cadence. Before automating anything, a 4-condition entry test: fail one and the loop costs more than a hand-written prompt.

  • The task repeats (weekly+) — otherwise one good prompt is cheaper.
  • Automated verification exists — a test/build/linter that can fail the work with nobody in the room.
  • The budget absorbs the waste — the loop re-reads, retries, explores; it burns tokens either way.
  • The agent has senior tools — logs, a repro environment, the ability to run what it writes.

The design — heartbeat wrapping /dev-loop

/loop sets the cadence; /goal continues until a condition is verified true by a separate model (maker ≠ checker in the stop condition); scheduled routines survive a restart. spec-loop is the ideal payload — it already brings the gate, the state, the skills, and the checker separation. Only the trigger is missing.

The security tax

An unattended loop is an unattended attack surface. It enters as an operational layer of the constitution: SAST + secret-scan + dependency-audit before any PR; audit each skill's origin before install (520 of 17,022 audited skills leaked credentials); non-verbose logging; re-audit permissions every 30 days, loop starts read-only; rotate the session before it bloats and hangs. Session hygiene is part of the tax.

Verdict. The playbook and spec-loop are different layers, not competitors — outer heartbeat vs rigorous inner loop. Your domain — fiscal/ARCA, payments, critical retail — sits squarely on the "do not autonomize" side, which is exactly the gated-by-design stance. The metric when you do autonomize: cost per accepted change. Below a 50% accept rate the loop is handing back the review work it came to remove.

Convergence"Loop engineering" (Jun 2026) reached these same principles independently. spec-loop only differs in that a person, not a cron, pulls the trigger — a decision, not a gap.
§12 · When NOT to use it

A mature methodology defines its own edges.

  • Spike / exploration. Throwaway code to learn. No SPEC; a note of what was learned. Whatever survives gets specified later.
  • Throwaway prototype. A demo that won't reach production. Marked as such, isolated, with a death date.

P0 hotfix

Production incident: you fix first. But the minimum evidence — what changed, how to roll it back — and the retroactive SPEC/ADR are mandatory within 24h. Without an escape valve, people cargo-cult the throwaways or abandon the method under pressure.

Why it mattersAn escape valve that's designed keeps the method honest. One that's improvised destroys it.

The generic layer that runs the methodology.

§14 · Reproduce on a team

Behavior lives in seven layers, not one file.

The skills are shareable, but the behavior does not live in a single settings.json. It is seven layers plus an external CLI plus a path gotcha.

LayerReproduced by
Configcopy settings.json/CLAUDE.md/output-style (+ fix paths)
Pluginsinstall from marketplace (engram, sonarqube)
Skillscopy ~/.claude/skills/ whole
Agents + commandscopy verbatim
Hookscopy (portable via $env:USERPROFILE)
External CLIgentle-ai via scoop, own bucket
MCP serversfree with Claude Code Desktop

Gotcha — hardcoded paths

settings.json carries the literal C:\Users\…. The bootstrap tokenizes the path on export and substitutes the local user on import.

Memory is not shared. engram + MEMORY.md are personal to each machine and build themselves as you work. Behavior is replicated; memory is earned.

Missed stepgentle-ai isn't in scoop's main bucket. Add the Gentleman bucket first or install fails with "couldn't find manifest".
§15 · Worked session

Idea to PR, without leaving one session.

A CAE gateway for ARCA (Java 21, Spring Boot, React, MSSQL), from idea to PR:

$ claude
> /discovery
  1×1 grill, proposes entities/endpoints, you decide 3 things
  ✓ CONTEXT · DOMAIN-MODEL · SPEC-001 · ADR-001/2/3
  ✓ ACCEPTANCE · RISKS · HANDOFF
> /dev-loop
  plan → coverage → build → QA loop → integration
  CONVERGED · PR opened. Stop at the merge.
> !python3 qa_ledger.py readiness --acceptance ACCEPTANCE.md
  READINESS: 88/100 — RELEASE CANDIDATE
> /sys-doc              # two-view deck from the ledger

The tool executes. The methodology governs. The evidence decides. The human approves.

Tracked-markdown protocol

Before modifying any tracked .md (CLAUDE.md, MODULE_DELTA, LEGACY_*, docs/), ask for the repo's current version first. Those files carry real progress — never regenerate from scratch.

The pointNo separate hand-off between phases. One session; the artifacts are the continuity.
