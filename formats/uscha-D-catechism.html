spec·loop the catechism · 01/17
The catechism · a methodology, questioned

Every good method survives being interrogated.

So here it is, put to the question. Uscha is spec-driven, tool-agnostic, and — its one heresy — it begins before the spec. The answers below are the method defending itself.

Instantiated in Claude Code via uscha-kit. Status is named where it matters: in the kit (implemented) · new (this version) · proposal (agreed, not yet coded).

Q01

Why begin before the specification exists?

Answer

Because the costly mistake isn't a bad implementation — it's a confident implementation of the wrong shape. A spec written over a misunderstood problem doesn't fix the misunderstanding; it makes it permanent and hard to see. So the first move is Discovery: turn a vague idea plus reference material into a proposed shape — entities, endpoints, boundaries — that the human accepts, bends, or rejects.

The order is the argument: idea → discovery → shape → spec → build → verify → evidence → human gate.

Only after the shape is agreed does anything get written down, and from there every step advances on captured evidence, halting short of the merge.

Q02

Why should the discovery interview argue with me?

Answer · in the kit

Because an agreeable interviewer just inherits your blind spots and hands them back formatted as a plan. Two skills sit at the front — /discovery for when you have an idea but no shape, /adr-refine for when the shape is known and only the edges need drawing. Neither writes code; both run on Read, Write, Glob, Grep.

the rule that defines them

Grill, don't agree. A discovery where the assistant agreed with everything has failed. The value lives in the questions — the contradictions, the fuzzy terms, the missing failure modes, the constraints you never said aloud. Friction is the product.

Q03

If it's all one chat, why write files at all?

Answer

Because the chat is the first thing to disappear. A new session, a /clear, a context compaction — each severs the assistant from everything merely said. Sub-agents can't read a conversation they weren't in; CI can't build from a memory; a teammate next week has no transcript. So discovery crystallizes the conversation straight into the repo as decisions settle:

CONTEXT.mdDomain glossary — kills fuzzy language.
DOMAIN-MODEL.mdThe approved shape: entities and relations.
SPEC.mdBehavior, I/O, errors, acceptance, rollback.
docs/adr/*.mdOne per durable decision — executable.
ACCEPTANCE.mdDoD as - [ ]; what readiness measures.
RISKS · HANDOFFResidual risk; what to read first.

Chat is where thinking happens. The repository is where it's remembered.

Q04

What's the difference between a SPEC and an ADR?

Answer

If it describes observable behavior — what must happen, with which inputs, outputs, and errors — it's a SPEC. If it justifies a choice between alternatives — why this shape and not another — it's an ADR. Nearly every non-trivial change needs a SPEC; only some warrant a formal ADR.

When is an ADR worth writing?

Only when the decision is hard to reverse, surprising without context, and the result of a real trade-off — all three, or it's noise that buries the decisions that matter. The Implementation Plan is what makes it executable: the agent reads it and builds without re-asking, and code links back with // ADR: <slug> so a later supersede finds everything it governed.

Q05

And what sits above the ADRs?

Answer · in the kit

The CONSTITUTION. An ADR chooses; the constitution forbids — it records the invariants no decision may override, whatever trade-off wins. An ADR may legitimately pick one datastore over another; an ADR may never pick "store the certificate in plaintext," because the constitution vetoed that before the alternatives were even discussed.

# CONSTITUTION.md — invariants, CWE-mapped
- Secrets never in logs or repo      # CWE-532/798
- Parameterized SQL only             # CWE-89
- Idempotency mandatory on CAE issue
- No merge without a human gate

Since 1.1.0 it's a versioned layer. A violation logs a BLOCKER — it caps readiness at ≤65 and blocks convergence by construction.

Q06

Doesn't all this rigor slow down small changes?

Answer

It would, if it were uniform — which is why it isn't. Every change opens with one question: what can this break, and what does the break cost? The answer sizes the apparatus. A profile-A tweak never drags the full machine behind it.

Q07

How does the build loop avoid running forever?

Answer · in the kit

By being engineered to converge rather than to perfect. The /dev-loop takes the ADRs plus acceptance, builds, and runs a severity-gated review cycle governed by three laws: converge, don't chase zero; tests are a guardrail, not the finale; generating tests is not running them.

It moves through plan → coverage gate (thin coverage triggers characterization tests) → build (one commit per step) → the QA loop (code-review, judgment-day, improve; apply fixes at or above the gate, defer the rest) → cross-repo integration → a final coverage pass → the PR, where it stops. An agent told to drive findings to zero will oscillate forever, so the loop watches for a period-2 fingerprint repeat and treats a clean cycle plus a clean static gate as done enough.

the failure it guards

The Ralph Wiggum loop: the agent emits the "done" token too early. Only an objective gate — never an opinion — closes it.

Q08

Why not let the agent report whether it passed?

Answer

Because if the maker writes its own report card, it can log exit_code: 0 having run nothing — not from malice, just the path of least resistance. So the ledger refuses to read the agent's account of reality. qa_ledger.py parses the actual artifacts:

coverage ← jacoco.xml
tests    ← surefire-reports/TEST-*.xml
static   ← checkstyle · pmd · spotbugs · findsecbugs

Absent is not "OK." A tool that didn't run is never invented as green.

This is maker ≠ checker: the one who makes doesn't graduate the work — a checker in fresh context does. It's Anthropic's evaluator-optimizer, articulated December 2024.

Q09

Which checks are allowed to stop the work?

Answer

Only the ones that read a fact. A gate over a fact — a byte comparison, a mutation result, a coverage number — may block. A gate that guesses over prose may only advise. The reason is behavioral: a natural-language heuristic that blocks throws false positives, the developer turns it off, and now there's a dead gate where a live one used to be.

GateReads
golden-diffbytes vs .approvedBLOCKS
pit-checkmutation XMLBLOCKS

Osmani's finding sharpens it: one uncorrelated checker caught 93.4% of what four caught. Stack different opinions, not four similar linters — and run fact gates in CI, not in the developer's face.

Q10

If the agent writes everything, what checks the agent?

Answer · new

The golden test — the one artifact the agent cannot author, which is precisely why it exists. A golden captures what the old code actually does, bugs and quirks included, by running it rather than reasoning about it, and freezes that as a human-approved .approved reference. After a migration, the new output is diffed against it byte for byte.

why it's sacred

If the agent authored the golden, it would encode the same partial understanding that lost the logic in the first place — and the diff would pass against its own mistake. It's a check on the agent, not one it grants itself.

  • Never let the agent generate or edit .approved — a PreToolUse hook blocks the write outright.
  • Capture by executing against real production corpus, never by reasoning about output.
  • Pin locale es-AR, freeze clocks, normalize GUIDs and map-order before serializing; add *.approved.* binary to .gitattributes or line endings will lie.
Q11

When is it safe to let the loop run itself?

Answer · proposal

Only when all four conditions hold, because failing one makes the loop cost more than a good prompt by hand:

  • The task repeats (weekly+).
  • Automated verification exists — a test/build/linter that fails the work without you.
  • The budget absorbs the waste — it re-reads and retries regardless.
  • The agent has senior tools — logs, a repro environment, the ability to run what it writes.

The outer loop is a heartbeat — /loop sets cadence, /goal continues until a separate model verifies the condition true — wrapping the inner /dev-loop, with the human still owning merge. And an unattended loop is an unattended attack surface, so autonomy arrives with an operational tax: secret-scan and dependency-audit before any PR, an origin check on every skill (520 of 17,022 audited leaked credentials), non-verbose logs, permissions re-audited on a schedule, sessions rotated before they bloat.

the honest verdict

Fiscal/ARCA, payments, critical retail all sit on the "do not autonomize" side the playbook itself marks. Gated-by-design isn't a gap — it's the decision. The metric once you do automate is cost per accepted change; below 50% accept, the loop is handing back the review it came to remove.

Q12

When should I NOT use Uscha?

Answer

A mature method names its own edges. Skip it for a spike — throwaway code to learn, no SPEC, just a note of what you learned; and for a throwaway prototype — marked, isolated, given a death date. For a P0 hotfix, you fix first, but the minimum evidence and a retroactive SPEC/ADR are due within 24 hours.

A designed escape valve keeps the method honest under pressure. An improvised one destroys it.

Q13

What actually runs it, and how do I set it up?

Answer · in the kit

Claude Code + Python + git/gh + the skills. The stack-specific parts (JDK/Maven, MSSQL, the linters) are the project's adapter, living in each repo's CLAUDE.md — not in the workbench.

# native installer — no Node, self-updating
curl -fsSL https://claude.ai/install.sh | bash
cp -r uscha-kit/.claude/skills/* ~/.claude/skills/
scoop install gentle-ai      # own bucket first — the missed step
claude --version && claude doctor

Cloning to a teammate is seven layers, not one file: config, plugins, skills, agents+commands, hooks, the external CLI, MCP servers. Watch the gotcha — settings.json hardcodes C:\Users\…, so the bootstrap tokenizes the path on export and rewrites it on import. And memory is not shared: engram and MEMORY.md are per-machine and earned as you work.

Q14

What does one full run actually look like?

Answer

A CAE gateway for ARCA — Java 21, Spring Boot, React, MSSQL — from idea to PR in a single session:

> /discovery
  ✓ CONTEXT · DOMAIN-MODEL · SPEC-001 · ADR-001/2/3
  ✓ ACCEPTANCE · RISKS · HANDOFF
> /dev-loop
  plan → coverage → build → QA loop → integration
  CONVERGED · PR opened. Stop at the merge.
> readiness --acceptance ACCEPTANCE.md
  88/100 — RELEASE CANDIDATE

The tool executes. The method governs. The evidence decides. The human approves.

Q15

Isn't this just chasing whatever's trending?

Answer

The opposite — it reached the durable ideas independently. "Loop engineering" surfaced in a single week of June 2026 and converged on the same principles this method already held: done-criteria that can fail, a hard iteration ceiling, maker ≠ checker, state externalized to disk, oscillation detection. The one deliberate difference is that a person pulls the trigger, not a cron — which is a decision, not a gap. And maker ≠ checker being Anthropic's evaluator-optimizer from December 2024 is the tell: this is the settled stuff, not the hype.
